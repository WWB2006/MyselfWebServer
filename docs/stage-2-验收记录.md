# 阶段 2 验收记录

> 填写方式：把「实际结果」列替换成你机器上的真实输出。
> 本阶段的核心是把「一个线程服务多个连接」跑通，并确认 ET 模式的循环读写没有漏读。
> 半包与粘包这两类现象要在这里第一次亲眼看到，它们是阶段 3 HTTP 解析器的输入。

## 二、功能验收

| 序号 | 检查项 | 命令 | 期望结果 | 实际结果 |
| --- | --- | --- | --- | --- |
| 1 | 构建 | `cmake --build build -j$(nproc)` | 无错误、无新增告警 |  |
| 2 | 单连接回显 | `nc 127.0.0.1 8080` | 输入内容原样返回 |  |
| 3 | 三连接并发（阶段 1 的缺陷已修复） | 开三个 `nc`，交替输入 | 三个连接都能独立收到自己的回显，互不阻塞 |  |
| 4 | 连接数增长 | 连续开 20 个 `nc` 连接 | 服务端逐个 accept，日志按 fd 打印，无积压 |  |
| 5 | ET 循环读（半包） | 用脚本分两次发送 `hello` + `world` | 服务端分两次读到，不丢字节、不产生假错误 |  |
| 6 | ET 循环读（粘包） | 用脚本一次发送 `aaaa` + `bbbb` | 一次事件里把两段都读出来，不残留 |  |
| 7 | 大块数据 | `nc` 粘贴一段 1MB 文本 | 全部回显，服务端不卡死、内存不持续增长 |  |
| 8 | 客户端中途断开 | `nc` 连接后 Ctrl+C，重复 10 次 | 服务端正确关闭 fd，`ss -tn` 中连接数回落 |  |
| 9 | 无 fd 泄漏 | 反复建连断开 200 次后 `ls /proc/$(pgrep webserver)/fd \| wc -l` | 数值回落，不持续增长 |  |

## 三、交付物核对

| 交付物 | 完成标准 | 状态 |
| --- | --- | --- |
| `Epoller` | 封装 `epoll_create1` / `epoll_ctl` / `epoll_wait`，返回活跃事件列表 | □ |
| `Channel` | fd 与关注事件的绑定，注册读/写/错误回调 | □ |
| `EventLoop` | 事件循环主体，`loop()` 中分发事件 | □ |
| `Buffer` | 读写缓冲，支持追加、取走、空间整理 | □ |
| `TcpConnection` / `Acceptor` | 连接对象与监听对象，负责装配读写回调 | □ |
| 关键点落实 | 所有连接 fd 加 `O_NONBLOCK`；ET 读循环到 `EAGAIN`；`accept` 循环到 `EAGAIN`；回调内只做轻量处理 | □ |

## 四、结论与遗留问题

结论：

| 问题 | 影响 | 计划 |
| --- | --- | --- |
| 只回显原始字节，浏览器无法直接访问 | 无法演示，也无法被 `curl` 验证 | 阶段 3 加入 HTTP 解析与静态文件服务 |
| 一次写入未考虑写缓冲 | 大响应可能只发出去一部分 | 阶段 4 起配合 `EPOLLOUT` 回填写缓冲 |
