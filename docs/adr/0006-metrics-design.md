# ADR 0006：运行指标与 /metrics 接口

- 状态：已采纳
- 日期：2026-09-27
- 相关阶段：阶段 7

## 背景

阶段 6 有了分级日志，但日志回答不了三个问题：

1. 现在有多少连接在线、峰值是多少；
2. 请求延迟的分布如何（P50/P95/P99），而不只是某一条慢请求的日志；
3. 外部监控系统（Prometheus、Grafana）怎么拿到这些数据。

## 选项

1. **解析日志统计**：不引入新代码，但每次查询都要扫日志文件，在线数值也不准确；
2. **保留每条请求的延迟样本**：能算精确分位，但需要无界存储或定期裁剪，内存与锁竞争不可控；
3. **固定桶直方图 + 原子计数器**：内存固定、竞争小，也是 Prometheus 官方推荐的直方图形式，
   分位由桶边界插值近似得到。

## 决定

采用方案 3，具体约定：

| 决定 | 内容 |
| --- | --- |
| 计数器 | 连接数（总数/当前/峰值）、请求数、错误数、读写字节数、按状态码类别与方法分类的请求数 |
| 延迟 | 12 个固定上界（1/2/5/10/20/50/100/200/500/1000/2000/5000 毫秒）加一档 `+Inf`，另有 sum 与 count |
| 分位 | 由桶内线性插值估算 P50/P95/P99，明确标注为近似值；精确分位交给 Prometheus 的 `histogram_quantile()` |
| 并发 | 所有计数器用 `std::atomic`，任意线程可上报；快照在调用线程内拼装 |
| 暴露方式 | `/metrics` 返回 Prometheus 文本格式；`/api/status` 返回 JSON 摘要 |
| 注册表 | `Metrics::install(&metrics)` 安装全局实例，net 层通过 `metrics::*` 便捷函数上报；未安装时为空操作，便于单元测试 |
| 依赖方向 | `util` 不依赖 `log`：日志行数由调用方作为参数传入渲染函数 |

命名规范：所有指标以 `myself_` 前缀，单位写在名字里（`_ms`、`_seconds`、`_total`），
`# TYPE` 注释与 Prometheus 约定一致。

## 代价

- 分位是近似值：如果延迟集中在两个桶边界之间，误差可能明显，桶边界需要按业务量级选择；
- 计数器只增不减，进程重启后归零，跨重启的趋势要靠 Prometheus 侧聚合；
- 全局注册表是单例风格，测试中必须 `reset()` 或重新 `install()`，否则用例互相影响；
- 每个请求多两次原子写（请求计数与桶计数），压测时要确认开销可接受。

## 后续观察

- 阶段 8 在 CI 里加一条指标一致性检查：压测后 `myself_requests_total` 与压测工具报告的成功请求数应接近；
- 阶段 9 用火焰图确认指标更新不在热点路径上；
- 如果将来需要按设备或接口维度打标签，评估引入标签化计数器（主要风险是标签基数）。
