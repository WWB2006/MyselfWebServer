# ADR 0003：主从 Reactor 与线程池

- 状态：已采纳
- 日期：2026-09-24
- 相关阶段：阶段 4

## 背景

阶段 3 的服务器是单线程 Reactor：一个线程同时负责 accept、读写、HTTP 解析与静态文件读取。
在单核上这已经够用，但有两个问题：

1. 多核机器上用不上第二个核，压测时 CPU 总是 100%/1 核；
2. 静态文件读取与响应构造都在事件循环线程里做，文件越大，其他连接的延迟抖动越明显。

## 选项

1. **每个连接一个线程**：实现简单，但连接数一多线程切换成本爆炸，不予考虑；
2. **单 Reactor + 计算线程池**：事件循环仍是一个线程，解析与文件读取丢给线程池，
   实现简单，但 accept 与所有读写事件仍挤在一个线程，网络吞吐受限于单核；
3. **主从 Reactor（one loop per thread）**：主线程只 accept，每条连接固定绑定到一个 IO 线程，
   再加一个可选的计算线程池处理耗时任务。

## 决定

采用方案 3，具体约定如下：

- 主线程运行 `baseLoop`，只注册监听套接字，负责 accept；
- `EventLoopThreadPool` 启动 N 个 `EventLoopThread`，每个线程一个 `EventLoop`，轮询分配新连接；
- **连接的生命周期绑定到它的 IO 线程**：连接对象在该线程内创建、注册事件、读写与销毁；
- `EventLoop` 增加跨线程任务投递能力：`runInLoop` / `queueInLoop`，用 **eventfd 唤醒**阻塞在
  `epoll_wait` 的线程；
- 增加通用 `ThreadPool` 处理耗时任务；任务若需要回写数据，必须通过
  `EventLoop::runInLoop` 回到连接所属的 IO 线程，禁止在 worker 线程直接操作 socket；
- 连接表由主线程插入、IO 线程删除，用互斥量保护；
- IO 线程数默认 4，`-t 0` 退化为单线程（用于做压测对比），worker 池默认关闭（`-w N` 开启）。

## 代价

- 事件循环不再是单线程独占，凡是跨线程的数据结构都必须加锁或改为消息传递；
- 调试复杂度上升：同一个请求可能先后在 worker 线程与 IO 线程执行，日志要带线程名；
- 线程数并非越多越好：连接数少时多线程反而增加切换开销，需要压测确定合适值；
- `EventLoop::updateChannel` 增加线程归属断言，写错线程会直接终止进程，这是有意的：
  越早暴露越好，否则表现为随机的偶发崩溃。

## 后续观察

- 阶段 5 引入定时器后，检查超时任务是否在所属 IO 线程执行；
- 阶段 9 用 ThreadSanitizer 跑一轮，确认没有遗漏的共享状态；
- 如果压测显示 worker 池收益不明显，考虑只在文件较大时才 offload（当前按 `/api/` 前缀区分）。
