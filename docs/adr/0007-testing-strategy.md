# ADR 0007：测试策略与持续集成

- 状态：已采纳
- 日期：2026-09-27
- 相关阶段：阶段 8

## 背景

阶段 0 到阶段 7 的验证方式都是手工的：改完代码用 `nc`、`curl`、`wrk` 手动确认。
这带来三个问题：

1. 每次改动都要重复手工步骤，回归成本随功能增加而上升；
2. 半包、粘包、超时、取消定时器这类边界场景很难靠手点覆盖；
3. 简历与面试里"有测试"这句话需要有可验证的证据（用例、报告、CI 记录）。

## 选项

1. **只把手工程序写成脚本**：成本最低，但无法验证内部状态，失败时定位困难；
2. **只写单元测试**：能覆盖核心逻辑，但无法验证"真实进程 + epoll + 多线程"的整体行为；
3. **单元测试 + 接口测试 + 持续集成**：成本最高，但覆盖最完整，且能持续防回归。

## 决定

采用方案 3，具体安排：

| 决定 | 内容 |
| --- | --- |
| 构建结构 | 把业务代码编成静态库 `myself_core`，`webserver` 可执行文件与单元测试分别链接 |
| 单元测试框架 | GoogleTest；优先 `find_package(GTest)` 用系统包，缺失时才 FetchContent 下载 |
| 单元测试范围 | Buffer、HttpParser、Router、Metrics、TimerQueue、LogStream |
| 接口测试 | pytest + `requests`，夹具启动**真实二进制**并轮询等待端口就绪，测试结束再终止 |
| 接口测试范围 | 200/404/HEAD/keep-alive/目录穿越、`/api/status` 字段、`/metrics` 格式与计数一致性 |
| 持续集成 | GitHub Actions：配置 → 构建 → `ctest` → `pytest`，失败时上传日志 artifact |
| 不放进 CI 的部分 | 性能回归（runner 性能抖动大，阶段 9 在固定机器上跑） |

## 代价

- 接口测试依赖固定端口与启动时序：同一台机器并行跑两份会冲突，已用环境变量与端口轮询缓解；
- FetchContent 在完全离线且没装 `libgtest-dev` 时会失败，这是刻意的取舍（保留联网路径，同时支持系统包兜底）；
- 单元测试依赖 `util/log/net` 模块可独立链接，因此阶段 8 顺带把 CMake 从"罗列源文件"改成"核心库 + 可执行文件"；
- 指标是全局单例，测试之间必须 `reset()`，否则用例互相污染；
- CI 只跑 Ubuntu，Windows 构建仍靠本地验证。

## 后续观察

- 阶段 9 补覆盖率统计（`gcov`/`lcov`）并把结果写进 README；
- 把阶段 7 验收记录里的"指标一致性"检查固化成接口测试（已完成），后续新增指标要同步补用例；
- 如果 CI 运行时间变长，优先缓存 GoogleTest 与 pip 依赖，而不是删减用例。
