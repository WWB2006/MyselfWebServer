# ADR 0009：开源来源标注与许可证

- 状态：已采纳
- 日期：2026-09-28
- 相关阶段：阶段 10

## 背景

项目在设计与实现过程中参考了开源项目（TinyWebServer、muduo），并在测试与工具链中使用
第三方组件（GoogleTest、wrk、FlameGraph）。这类项目在面试与公开仓库中会被追问两件事：

1. 哪些代码是参考别人的，哪些是自己写的；
2. 分发时是否满足上游许可证要求。

## 选项

1. **不声明来源**：仓库看起来"更纯粹"，但一旦被比对出来，诚信问题比技术问题严重得多；
2. **声明来源但许可证随意选**：容易在分发时违反上游条款（尤其是 GPL 系）；
3. **声明来源、选择宽松许可证、逐个记录第三方组件**：多做一步文档工作，但风险最低。

## 决定

采用方案 3：

| 决定 | 内容 |
| --- | --- |
| 参考来源 | README 的"与参考项目的差异"一节列出参考项目，并说明核心模块自行实现 |
| 许可证 | 项目自身采用 MIT，见根目录 `LICENSE` |
| 代码边界 | 不复制上游代码；参考的是设计思路（Reactor 结构、线程模型、状态机划分） |
| 第三方组件 | GoogleTest（测试）、wrk（压测）、FlameGraph（可视化）仅在开发与测试中使用，不随产物分发；各自许可证见其仓库 |
| 依赖引入 | 若后续引入运行时第三方库（如 json、日志库），必须在 README 与本 ADR 中补充名称、版本与许可证 |
| 提交历史 | 保留真实提交节奏，不使用"一次性导入"的提交掩盖开发过程 |

## 代价

- README 与 ADR 各多出一节内容，维护成本略增；
- 如果将来把项目改造成闭源分发，需要重新核对每个依赖的许可证类型；
- MIT 许可证本身不提供专利授权条款，若项目进入商业场景，需要重新评估（可考虑 Apache-2.0）。

## 后续观察

- 引入任何新依赖时，同步更新本节与 README；
- 如果发布 Docker 镜像或二进制包，检查是否把测试依赖误打进产物；
- 面试前确认 README 中的来源声明与实际代码一致，避免出现"声明与实现不符"。
