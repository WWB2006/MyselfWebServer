# ADR 0008：性能验证与健壮性加固

- 状态：已采纳
- 日期：2026-09-27
- 相关阶段：阶段 9

## 背景

阶段 8 之后代码有测试保护，但还缺三样东西：

1. **性能证据**：只有一个压测样本，没有并发矩阵与原始数据，无法回答"瓶颈在哪里"；
2. **热点定位手段**：出问题只能靠猜，没有火焰图；
3. **过载与退出路径**：连接数无上限，被压垮时表现为随机超时而不是明确的 503；
   Ctrl+C 直接结束进程，缓冲里的日志与在途请求都没有收尾。

同时，压测环境本身也需要规范化：客户端与服务端跑在同一台虚拟机会互相抢 CPU，
数据没有说服力。

## 选项

1. **只补一个压测脚本**：成本最低，但无法定位瓶颈，也无法证明稳定性；
2. **压测 + 火焰图**：能定位热点，但过载与退出路径仍然不可控；
3. **压测矩阵 + 火焰图 + 故障注入 + 长稳采样 + 过载保护与优雅退出**：覆盖最完整。

## 决定

采用方案 3：

| 决定 | 内容 |
| --- | --- |
| 压测方法 | `scripts/bench_matrix.sh` 按并发梯度（如 1/10/50/100/200/500）依次压测，逐条写入 CSV，并记录环境（核数、内存、编译类型） |
| 客户端位置 | 压测客户端必须跑在宿主机或另一台机器上；同机压测的结果只作参考，必须在文档中注明 |
| 热点定位 | `scripts/flamegraph.sh` 用 `perf record` 采样运行中的进程，配合 FlameGraph 生成 SVG，存放 `docs/bench/` |
| 故障注入 | `scripts/fault_injection.py` 用原始 socket 覆盖六类场景：半包、粘包、慢连接、超长请求头、超长请求体、连接抖动 |
| 长稳采样 | `scripts/soak_test.sh` 在压测期间每 30 秒采样 RSS、在线连接数、错误数，输出 CSV 与首尾对比 |
| 过载保护 | 新增 `-m/--max-connections`：超过上限的新连接立即回 503（尽力而为）并关闭，同时累加 `myself_connections_rejected_total` |
| 优雅退出 | SIGINT/SIGTERM 只设置原子标志；事件循环用 200ms 定时器检查标志，触发后停止接收、关闭所有连接、停线程池与异步日志、刷盘再退出 |
| 数据归档 | 所有原始输出进 `docs/bench/`，README 只引用文件与结论，不粘贴大段日志 |

## 代价

- 过载时返回 503 需要写一个响应，极端情况下写操作本身也可能失败，此时直接关闭连接；
- 优雅退出依赖定时器轮询标志（200ms 粒度），不是严格的实时响应；
- 长稳测试需要数小时到数十小时的机器时间，且必须在压测客户端不被中断的前提下进行；
- `perf` 在受限环境（容器、无 `CAP_PERFMON`）可能无法采样，脚本会检测并给出替代方案（`/proc/<pid>/stat` 采样或 ASan/Valgrind 检查）。

## 后续观察

- 压测数据若显示 CPU 已饱和而 QPS 不再增长，说明该换更高并发模型（如 io_uring、多队列）；
- 若 `myself_connections_rejected_total` 长期为 0 而延迟上升，说明瓶颈不在连接数，需要看火焰图；
- 阶段 10 收尾时，把压测数据、火焰图与长稳结论整理进 README 的"数据与结论"一节。
